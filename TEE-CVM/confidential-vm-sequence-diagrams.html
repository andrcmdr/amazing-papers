CVM Boot Sequence

AMD SEV-SNP
sequenceDiagram autonumber participant User as 👤 User/Tenant participant ARM as ☁️ Azure Resource Manager participant Host as 🖥️ Host Server participant HV as Hypervisor participant ASP as 🔐 AMD Secure Processor participant CVM as 🛡️ Confidential VM User->>ARM: Create CVM (DCasv5/ECasv5) ARM->>Host: Allocate host with SEV-SNP CPU Host->>HV: Initialize VM context rect rgb(40, 20, 20) Note over HV,ASP: Hardware Security Initialization HV->>ASP: Request new VM encryption key ASP->>ASP: Generate unique AES-256 key ASP-->>HV: Return VM key handle (key never exposed) HV->>ASP: Create SNP Guest context ASP->>ASP: Initialize RMP (Reverse Map Table) end rect rgb(20, 40, 60) Note over ASP,CVM: Secure Boot Phase ASP->>CVM: Initialize encrypted memory pages CVM->>CVM: UEFI Secure Boot starts CVM->>CVM: Verify firmware signatures CVM->>CVM: Initialize vTPM in protected memory CVM->>CVM: Measure boot components → PCRs end rect rgb(20, 50, 20) Note over CVM: Guest OS Boot CVM->>CVM: Load & verify bootloader CVM->>CVM: Load Linux/Windows kernel CVM->>CVM: Kernel initializes (sees normal memory) CVM-->>User: VM Ready - SSH/RDP available end
Key Steps
1 AMD Secure Processor generates a unique per-VM AES-256 encryption key that never leaves the CPU die
2 RMP (Reverse Map Table) tracks page ownership to prevent hypervisor tampering
3 vTPM initializes inside encrypted memory, invisible to hypervisor
4 Guest OS boots normally - memory encryption is transparent to workloads

4 Only after successful attestation are secrets released from Key Vault

Runtime Memory Protection

SEV-SNP
sequenceDiagram autonumber participant App as 📱 CVM Application participant MMU as CPU MMU participant ENC as 🔐 Memory Encryption Engine participant RAM as 💾 Physical RAM participant HV as ⚠️ Hypervisor participant RMP as RMP Table Note over App,RAM: Normal Memory Access (from inside CVM) App->>MMU: Read virtual address 0x1000 MMU->>MMU: Translate VA → PA (0xABCD000) MMU->>RMP: Check page ownership RMP-->>MMU: Page owned by this VM ✓ MMU->>ENC: Request physical address ENC->>RAM: Read encrypted bytes RAM-->>ENC: Return ciphertext ENC->>ENC: Decrypt with VM's key ENC-->>App: Return plaintext data ✓ Note over HV,RAM: Malicious Access Attempt (from hypervisor) HV->>RAM: Direct read 0xABCD000 RAM-->>HV: Return ciphertext only ✗ Note right of HV: Sees random bytes
No decryption key HV->>RMP: Attempt to remap page RMP-->>HV: DENIED - page is private ✗ Note right of HV: #VC exception or
VM termination
Key Steps
1 Memory encryption/decryption happens automatically in the CPU's memory controller
2 RMP (Reverse Map Table) prevents hypervisor from remapping or accessing private pages
3 Hypervisor can only see encrypted ciphertext - no access to decryption keys
4 Any tampering attempt triggers hardware exception or VM termination

Confidential GPU Initialization (H100)

NCC H100 v5
sequenceDiagram autonumber participant App as 🤖 AI/ML Application participant Driver as 🔧 NVIDIA Driver (in TEE) participant CPU as 🔐 CPU TEE (SEV-SNP) participant PCIe as 🔗 PCIe Bus participant GPU as 🎮 H100 GPU participant HBM as 💾 GPU HBM3 Memory Note over Driver,GPU: Secure Channel Establishment Driver->>GPU: Initiate SPDM session GPU->>GPU: On-die RoT generates session key GPU-->>Driver: SPDM challenge-response Driver->>Driver: Verify GPU attestation Driver-->>GPU: Establish AES-GCM channel ✓ Note over App,HBM: Secure Data Transfer App->>Driver: cudaMemcpy(data, GPU) Driver->>CPU: Encrypt data for GPU CPU->>CPU: AES-GCM encrypt + sign CPU-->>PCIe: Encrypted bounce buffer PCIe->>GPU: Ciphertext over PCIe GPU->>GPU: Decrypt with session key GPU->>HBM: Store in encrypted HBM3 Note over App,HBM: Secure Computation App->>Driver: Launch CUDA kernel Driver->>GPU: Encrypted kernel + params GPU->>GPU: Decrypt & execute kernel GPU->>HBM: Process in encrypted memory HBM-->>GPU: Encrypted results GPU->>PCIe: Encrypt output for CPU PCIe-->>Driver: Return to TEE Driver-->>App: Decrypted results ✓ Note over Driver,GPU: Combined Attestation App->>Driver: Request attestation Driver->>CPU: Get CPU attestation report Driver->>GPU: Get GPU attestation report Driver->>Driver: Combine reports Driver-->>App: Joint CPU+GPU evidence
Key Steps
1 SPDM session establishes encrypted channel between CPU TEE and GPU using AES-GCM
2 Data traverses PCIe bus encrypted - even physical interposers see only ciphertext
3 GPU HBM3 memory (94GB) is encrypted with hardware key in GPU's on-die RoT
4 Combined attestation proves both CPU and GPU are in confidential mode

Runtime Memory Protection

Intel TDX
sequenceDiagram autonumber participant App as 📱 TD Application participant TD as 🛡️ Trust Domain participant TDX as 🔐 TDX Module participant TME as 🔑 TME-MK Engine participant RAM as 💾 Physical RAM participant VMM as ⚠️ VMM/Hypervisor Note over App,RAM: Normal Memory Access (TD internal) App->>TD: Access virtual address TD->>TDX: Memory access via SEPT TDX->>TDX: Verify TD owns page (SEPT walk) TDX->>TME: Request decryption (KeyID = TD's key) TME->>RAM: Read encrypted cache line RAM-->>TME: Return ciphertext TME->>TME: AES-XTS decrypt (TD KeyID) TME-->>App: Plaintext data ✓ Note over VMM,RAM: VMM Access Attempt VMM->>RAM: Direct memory read RAM-->>VMM: Returns ciphertext ✗ Note right of VMM: No key access VMM->>TDX: Attempt EPT modification TDX->>TDX: Check SEPT ownership TDX-->>VMM: #VE (Virtualization Exception) ✗ Note over TDX: Integrity Check TDX->>TDX: Verify MAC on page access alt Integrity Valid TDX-->>TD: Allow access ✓ else Integrity Violation TDX->>TDX: Terminate TD immediately Note over TD: Security violation detected end
Key Steps
1 TME-MK (Total Memory Encryption - Multi-Key) provides per-TD encryption keys
2 SEPT (Secure EPT) tracks page ownership - VMM cannot modify TD's page tables
3 VMM access triggers #VE exception - cannot read or write TD memory
4 Memory integrity checking detects tampering and terminates TD if violated
